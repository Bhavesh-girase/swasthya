# Swasthya-Vaani

A voice-first post-discharge follow-up **prototype** for India. This first build is a password-protected dashboard with fictional cases and an optional Sarvam language preview. It does not make phone calls, send alerts, store patient records, or provide medical advice.

## Run locally

From this folder, keep the existing `.env` and add these settings to it (do not replace your Sarvam key):

```env
DASHBOARD_USERNAME=care-team
DASHBOARD_PASSWORD=choose-a-long-unique-password
SESSION_SECRET=choose-a-separate-long-random-secret
APP_ENV=development
```

Then run in Windows CMD:

```cmd
python -m pip install -r requirements.txt
python -m uvicorn swasthya.main:app --host 127.0.0.1 --port 8000 --reload
```

Open <http://127.0.0.1:8000>. For the full showcase, click **Run voice demo**: Sarvam Bulbul generates a fictional Hindi caller utterance, Saaras transcribes the short 8 kHz audio, Sarvam 105B Conversations drafts a constrained acknowledgement, and Bulbul speaks the reply. This makes four Sarvam API requests using only the fixed synthetic scenario; it uses no microphone, phone number, or patient record. The smaller **Preview acknowledgement** also uses fixed synthetic text. Urgent examples use a fixed safety message and never call the model.

The app reads `SARVAM_API_KEY` and dashboard settings from the process environment first, then from `.env`. The key is used only by the server and is never sent to the browser. `.env` is ignored by Git and excluded from the container.

## Container build

```cmd
docker build -t swasthya-vaani .
docker run --rm -p 127.0.0.1:8000:8000 --env-file .env -e APP_ENV=development swasthya-vaani
```

For a hosted deployment, terminate HTTPS at the platform or a trusted reverse proxy, set `APP_ENV=production`, configure the dashboard credentials and a session secret of at least 32 random bytes as platform secrets, and restrict access to the care team. Add platform-level login rate limits/network restrictions. The container runs as a non-root user. `/healthz` is a non-sensitive health check. Do not deploy real patient data to this prototype.

## Safety and next production gates

- The dashboard triage labels are fictional fixtures; they are not generated by Sarvam or a clinical decision system.
- A real workflow needs clinician-approved scripts, patient consent and opt-out, human escalation coverage, tested language/dialect quality, privacy/retention policy, and security review before any patient data is used.
- Sarvam model APIs provide language/speech capabilities, not phone dialing or SMS. Sarvam Voice Agents supports deployments and outbound campaigns, but uses separate Voice Agents credentials, organization/workspace setup, and telephony configuration. Keep live campaigns disabled until those are explicitly configured and clinically approved.
- Use an India-hosted, encrypted database and a managed secrets store before storing any real records. This prototype intentionally has no patient database.

## Sarvam APIs used / planned

- Language preview: [`sarvam-105b-conversations`](https://docs.sarvam.ai/api-reference-docs/api-guides-tutorials/chat-completion/overview).
- Future call-audio transcription: [`saaras:v4`](https://docs.sarvam.ai/api-reference-docs/api-guides-tutorials/speech-to-text/rest-api); synchronous REST is limited to 30 seconds, so longer/live calls need batch or streaming.
- Future regional speech: [`bulbul:v4-flash`](https://docs.sarvam.ai/api-reference-docs/api-guides-tutorials/text-to-speech/rest-api), using voice IDs validated for each language.
- Outbound calling: [Sarvam Voice Agents](https://docs.sarvam.ai/voice-agents/api/introduction), a separate product/API from the model SDK.
